# Database Migrations Guide

This guide explains how to manage database migrations in the Career Elevate Backend using Alembic.

## Overview

We use **Alembic** for database migrations, which provides:
- ✅ Version control for database schema
- ✅ Automatic migration generation
- ✅ Safe upgrade/downgrade operations
- ✅ Team collaboration on schema changes

## Quick Start

### 1. Install Dependencies
```bash
pip install -r requirements.txt
```

### 2. Start PostgreSQL
```bash
docker-compose up -d postgres
```

### 3. Create Initial Migration
```bash
python migrate.py init
```

### 4. Apply Migration
```bash
python migrate.py upgrade
```

## Migration Commands

### Using the Helper Script (Recommended)

```bash
# Create initial migration
python migrate.py init

# Create a new migration
python migrate.py create "Add user table"
python migrate.py create "Add email index to users"

# Apply migrations
python migrate.py upgrade              # Upgrade to latest
python migrate.py upgrade +2           # Upgrade 2 versions forward
python migrate.py upgrade <revision>   # Upgrade to specific revision

# Rollback migrations
python migrate.py downgrade            # Downgrade 1 version
python migrate.py downgrade -2         # Downgrade 2 versions
python migrate.py downgrade <revision> # Downgrade to specific revision

# Check status
python migrate.py current             # Show current revision
python migrate.py history             # Show migration history
python migrate.py status              # Show detailed status

# Reset database (⚠️ DANGER!)
python migrate.py reset               # Drops all data and rebuilds
```

### Using Alembic Directly

```bash
# Generate new migration
alembic revision --autogenerate -m "Migration message"

# Apply migrations
alembic upgrade head
alembic upgrade +1
alembic upgrade <revision_id>

# Rollback migrations
alembic downgrade -1
alembic downgrade <revision_id>
alembic downgrade base  # ⚠️ Drops all tables

# Information commands
alembic current
alembic history
alembic show <revision_id>
```

## Migration Workflow

### 1. Making Model Changes

Edit your SQLAlchemy models in `models/schema.py`:

```python
# Add a new field
class UserModel(Base):
    __tablename__ = "users"
    
    id = Column(Integer, primary_key=True)
    name = Column(String(100), nullable=False)
    email = Column(String(255), unique=True, index=True)
    phone = Column(String(20), nullable=True)  # ← New field
    created_at = Column(DateTime(timezone=True), server_default=func.now())
```

### 2. Generate Migration

```bash
python migrate.py create "Add phone field to users"
```

This creates a new migration file in `migrations/versions/` with:
- Unique revision ID
- Upgrade operations (add column)
- Downgrade operations (drop column)

### 3. Review Migration

Check the generated migration file:
```python
def upgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.add_column('users', sa.Column('phone', sa.String(length=20), nullable=True))
    # ### end Alembic commands ###

def downgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_column('users', 'phone')
    # ### end Alembic commands ###
```

### 4. Apply Migration

```bash
python migrate.py upgrade
```

## Best Practices

### 1. Always Review Generated Migrations
- Alembic auto-generates migrations but may miss complex changes
- Always review before applying to production
- Test migrations on a copy of production data

### 2. Use Descriptive Messages
```bash
# Good
python migrate.py create "Add phone and address fields to users"
python migrate.py create "Create orders table with foreign keys"

# Bad  
python migrate.py create "update"
python migrate.py create "changes"
```

### 3. Test Both Upgrade and Downgrade
```bash
# Apply migration
python migrate.py upgrade

# Test rollback
python migrate.py downgrade -1

# Re-apply
python migrate.py upgrade
```

### 4. Backup Before Major Migrations
```bash
# Backup PostgreSQL database
docker-compose exec postgres pg_dump -U career_elevate_user career_elevate > backup.sql
```

### 5. Team Collaboration
- Commit migration files to version control
- Coordinate migration timing with team
- Apply migrations in order of creation

## Common Migration Scenarios

### Adding a Column
```python
# models/schema.py
class UserModel(Base):
    # ... existing fields ...
    new_field = Column(String(100), nullable=True)
```

### Removing a Column
```python
# Remove from model first, then generate migration
# The migration will include the drop_column operation
```

### Changing Column Type
```python
# Change in model
age = Column(Integer)  # was String before

# May require manual migration adjustment for data conversion
```

### Adding Indexes
```python
# In model
email = Column(String(255), index=True)  # Add index=True

# Or in migration
op.create_index('ix_users_email', 'users', ['email'])
```

### Adding Foreign Keys
```python
# In model
user_id = Column(Integer, ForeignKey('users.id'))

# Migration will auto-generate foreign key constraint
```

## Troubleshooting

### Migration Conflicts
If multiple developers create migrations simultaneously:
```bash
# Merge conflicts in migration history
alembic merge -m "Merge migrations" <revision1> <revision2>
```

### Failed Migration
```bash
# Check current state
python migrate.py current

# Force revision (if migration partially applied)
alembic stamp <revision_id>

# Try upgrade again
python migrate.py upgrade
```

### Reset Everything (Development Only)
```bash
python migrate.py reset  # ⚠️ Deletes all data!
```

## Migration Safety Checklist

Before applying migrations to production:

- [ ] Migration tested on development copy
- [ ] Database backup created
- [ ] Migration is reversible (downgrade tested)
- [ ] Team notified of schema changes
- [ ] Application code compatible with new schema
- [ ] Indexes/constraints won't cause downtime
- [ ] Data migration scripts tested (if needed)
